# 인터프리터

- 프로그램 전체를 독립적인 기계어 실행 파일로 미리 만들어 두지 않고,실행 과정에서 코드를 해석하고 그 의미를 수행한다.
- "코드를 한 줄씩 번역해서 실행한다"라는 설명은 단순화된 표현이다.
- 실제로는 여러 줄을 한꺼번에 분석하거나, 소스 코드를 중간 언어 혹은 바이트코드로 변환한 뒤 이를 실행하기도 한다.
- **컴파일러와 반대되는 개념이 아니다.** 인터프리터는 작성된 코드를 동작시키기 위해 언어를 처리하는 구현 방식이다.

### 인터프리터가 하는 일

- 소스 코드 분석
- 연산 수행
- 변수와 함수 관리
- 조건문과 반복문 처리
- 메모리 및 객체 관리
- 오류 검출과 보고
- OS 기능 호출 등

### 동작 과정

1. 소스 코드 읽기

1. 어휘 분석

	- 문자열로 이루어진 코드를 의미 있는 최소 단위인 **토큰**으로 나눈다.

1. 구문 분석(Syntax Analysis)

	- 토큰들이 문법에 맞게 배치되었는지 확인하고, 코드의 구조를 나타내는 구문 트리를 만든다.
	- 구문 트리 중 대표적인 표현이 AST(Abstract Syntax Tree, 추상 구문 트리)이다.

1. 의미 분석(Semantic Analysis)

	- 구문 분석에서 문법적으로 올바르게 코드가 작성되었는지를 확인했다면, 의미 분석에서는 실제 의미가 올바른지 확인한다.

    	> 선언되지 않은 변수를 사용했는가?\
		> 함수에 전달된 인자의 개수가 올바른가?\
		>허용되지 않는 타입끼리 연산했는가? 등

	- 의미 분석을 함에 있어서, 정적 타입 언어는 실행 전에 검사를 수행하나 동적 타입 언어는 일부 검사를 실제로 구문이 실행되기 전까지 미룰 수 있다.

    	> 여기서 정적 타입 언어(Static Typed Lang.)란 C, C++, C#, Java등을 말하고,\
		> 실제 실행되기 전에 int num = "hello"처럼 불가능한 연산이나 선언이 있을 경우 컴파일 단계에서 타입 검사 후 실행 파일을 생성하지 않는다.\

		> 동적 타입 언어(Dynamic Typed Lang.)란 파이썬, JavaScript, Ruby 등을 말하고,\
		> 변수에 타입이 붙는 것이 아니라 값에 타입이 붙는다. 검사 자체는 실제로 해당 라인이 실행될 때 수행한다.
		> 사전에 검사를 수행하지 않았고 실행 중에 검사하여 오류가 검출되므로 Runtime Error를 발생시킨다.\
		> 다만, 동적 타입 언어도 기본적인 문법 검사, 토큰화 정도는 실행 전에 수행한다.
		>> 실행이 될 때가 와서야 검사하는 이유는, 시스템의 설계상 값이 타입을 가지고, 연산할 때가 되어서야 실제 값에 맞는 동작을 결정하기 때문이다.

		> **단! 정적 타입 언어라고 해서 전부 컴파일러를 사용하는 것은 아니며, 동적 타입 언어라고 해서 전부 인터프리터를 사용하는 것도 아니다.**\
		>정적 타입 언어는 것은 표현식과 연산의 타입 호환성을 주로 검사하며 일반적으로 프로그램 실행 전에 표현식의 타입이 결정되거나 검증되고,\
		>동적 타입 언어는 프로그램 실행 중 실제 값의 타입을 바탕으로 연산 가능 여부를 검사한다.
		>인터프리터/컴파일러 사용의 차이는 코드를 어떻게 실행하는가(실행 방식)?의 차이이므로, 두개는 확실하게 분리하여 숙지해야 할 개념이다.\
		>예를 들어 C#은 정적 타입 언어이면서 중간 코드로 컴파일된다. .NET런타임은 이 중간 코드를 JIT 또는 AOT 방식으로 네이티브 코드로 변환하여 실행할 수 있다. 따라서 중간 코드를 사용한다는 점만으로 순수하게 인터프리터 방식이라고 할 수 없다.

1. 중간 언어 생성 / 직접 실행

    - 인터프리터의 구현에 따라 방식이 달라진다.

    1) AST 직접 실행

    	- AST의 각 노드를 순회하면서 그 의미를 바로 수행한다.
    	- 구현은 단순하나 같은 구조를 반복해서 순회해야 하므로 성능이 낮을 수 있다.

    1) 바이트코드 생성 후 실행

    	- AST를 더 단순한 명령어 형태인 바이트코드로 변환하고, 가상 머신이 이를 실행한다.

1. 실행

### "한 줄 씩 실행" 설명의 한계

- 틀린 말은 아니지만 정확하지도 않다. 최대한 요약한 표현인 셈.

- 예를 들어 조건문의 경우, 말 그대로 한 줄 씩 실행하면 완성된 의미를 수행할 수 없다.

    ```python
	if True:
    	print("hello")
	```
	
- 보통 현대의 인터프리터는 보통 하나의 `표현식`, `문장`, `함수`, `코드 블록`, `모듈`, 혹은 `소스 파일 전체`를 먼저 분석한다.

- 따라서 인터프리터는 `코드를 실행 과정에서 해석하지만, 반드시 한 줄 단위로 번역하는 것은 아니다`라고 요약하는 것이 더 정확하다.

### 구성 요소

구현마다 차이가 있으나, 일반적으로 아래의 항목을 포함한다.

1. 프런트엔드

	- 소스 코드를 이해할 수 있는 구조로 변환한다.
	- `렉서`혹은 `토크나이저`, `파서`, `의미 분석기`, `AST생성기`

1. 실행 엔진

	- 분석된 코드의 의미를 실제로 수행한다.
	- `AST평가기`, `바이트코드 가상 머신`, `JIT컴파일러`, `함수 호출 및 제어 흐름 처리기`

1. 런타임 시스템

	- 프로그램이 실행되는 동안 필요한 환경을 제공한다.
	- `객체 및 타입 시스템`, `메모리 관리`, `가비지 컬렉션`, `예외 처리`, `모듈 로딩`, `표준 라이브러리`, `입출력 및 운영체제 연동`

위의 구성 요소들로 인해, 인터프리터는 단순한 번역기라기 보단 언어의 실행 환경 전체에 가까운 경우가 있다.

### 종류

#### 실행 대상에 따른 분류
1. 트리 순회 인터프리터

	- AST를 직접 순회하며 실행한다.

	- 장점

    	1) 구조가 직관적
		1) 구현 난이도가 비교적 낮음
		1) 언어 실험 혹은 교육용 구현에 적합

	- 단점
	
    	1) 트리를 반복해서 탐색해야 하므로 성능이 낮아질 수 있다.
		1) 노드마다 간접 호출이나 분기 비용이 발생한다.
		1) 일반적으로 바이트코드 방식보다 느리다.

1. 바이트코드 인터프리터

	- 소스 코드를 바이트코드로 변환한 뒤 가상 머신이 이를 읽어 실행한다.
	- 대표적으로 CPython이 있다.
    	> 소스코드 - 토큰화/파싱 - AST - 바이트코드 - Python가상 머신에서 실행

	- 장점

    	1) AST보다 명령이 단순하고 크기가 작다.
		1) 반복 실행에 유리하다.
		1) 최적화 적용이 쉽다.
		1) CPU나 OS에 덜 종속적인 중간 표현을 사용할 수 있다.

	- 단점

    	1) 실제 CPU보다는 실행 오버헤드가 크다
		1) 가상 머신을 별도로 구현해야 한다.

#### 가상 머신의 명령어 구조에 따른 분류

1. 스택 기반 가상 머신

	- 연산에 필요한 값을 스택에 넣고 꺼내며 실행한다.

	- 장점

    	1) 명령어 구조와 구현이 단순하다.

	- 단점
       
	    1) 값을 넣고 꺼내는 명령이 많아질 수 있다.

	- 추가적으로, 스택 기반 인터프리터에서 말하는 '스택'은 스택 기반 가상 머신의 Operand Stack은 명령어가 피연산자를 저장하고 사용하는 추상적인 LIFO 스택이다. 특정한 물리적 메모리 영역을 의미하지 않으며, 실제 저장 방식은 VM 구현에 따라 달라질 수 있다.
	- 성능이 떨어질 수 있다고 하는건, 상대적으로 느린 CPU의 스택 영역 반복접근 때문이 아니라, 단순히 명령어 수가 많아지기 때문. 다른 방식으로는 한 줄이면 끝날 구문을, 상대적으로 훨씬 많은 수의 단순한 명령어의 뭉치가 된다.
	- 다만 이 방식에 JIT이 끼게 되면 명령어가 단순화되면서 다른 방식(레지스터 기반 등)과의 차이가 거의 드러나지 않는다.
	- 여기서 JIT이 낀다는 것은, JIT컴파일러가 자주 실행되는 바이트코드를 네이티브 기계어로 변환하면, 해당 코드에서는 바이트코드를 매번 해석하고 디스패치하는 오버헤드가 크게 줄어들며, 이렇게 최적화된 코드에서는 스택 기반과 레지스터 기반 바이트코드의 차이가 거의 드러나지 않는다는 뜻이다.

	- 안드로이드의 Dalvik VM이 JVM과 달리 레지스터 기반 VM을 선택했는지의 핵심 이유도 이와 관련되어 있다.

    	> 예전의 모바일 CPU는 비교적 성능이 굉장히 낮았기 때문에, 인터프리터가 해석해야 하는 바이트코드의 명령어 수를 최대한 줄이는 것이 중요했다고 한다. 당장 명령어 자체가 복잡해지더라도 명령어의 수를 줄이면 성능면에서 이점을 가져올 수 있었다고 한다.\
		>추후 JVM의 StackFrame, Operand Stack, Local Variable Table, CPU레지스터와 가상 레지스터의 관계를 알게 되면 위의 문제가 이해될거라고한다..

1. 레지스터 기반 가상 머신

	- 가상 레지스터에 값을 저장하면서 명령을 수행한다.

	- 장점

    	1) 동일한 작업에 필요한 명령어 수를 줄일 수 있다.

	- 단점

    	1) 명령어의 표현과 VM구현은 더 복잡해질 수 있다.

### 인터프리터의 장점

1. 빠른 개발과 실행

	- 별도의 빌드 과정 없이 소스 코드를 곧장 실행할 수 있어 코드 수정과 확인에 소요되는 시간을 줄일 수 있다.

1. 대화형 실행 환경

	- REPL을 제공하기 좋다.

    	1) Read
			- 사용자의 입력 받기
		1) Eval
			- 입력 평가
		1) Print 
    		- 결과 출력
		1) Loop
			- 다시 입력 대기

1. 높은 이식성

	- 동일한 인터프리터 혹은 가상 머신이 설치되어 있다면 다른 OS에서도 같은 코드를 실행할 수 있다.
	- 다만, 코드에 운영체제별 API, 네이티브 라이브러리, 파일 경로 등에 의존하게 되면 이식성이 낮아진다.

1. 동적인 기능을 구현하기 용이하다.

	- `런타임 타입 검사`, `동적 코드 로딩`, `동적 평가`, `리플렉션`, `실행 중 객체 구조 변경`, `대화형 디버깅` 등의 기능을 제공하기 용이하다.

1. 오류 위치를 이해하기 쉬운 경우가 많다.

### 인터프리터의 단점

1. 실행 성능 오버헤드

	- 프로그램의 의미를 실행 중에 계속 처리해야 한다. 따라서 이미 기계어로 변환된 프로그램보다 **추가 작업**이 많다.

1. 실행 환경이 갖춰져야 함

	- 알맞은 언어의 인터프리터 또는 런타임이 설치되어있는 환경이어야 한다.

	- 반면 네이티브 컴파일된 프로그램은 필요한 라이브러리만 있으면 독립적인 실행 파일로 배포할 수 있다.

1. 일부 오류가 늦게 발견됨.

	- 실행한 적 없는 코드의 경우 오류가 발견되지 않을 수 있다.

1. 소스 코드 보호 및 배포상의 한계.

	- 소스 코드 자체를 배포하는 경우 구현이 노출될 수 있고, 바이트코드로 배포하는 경우에도 역분석이 가능하다.

### 인터프리터가 네이티브 컴파일보다 유리한 환경

1. 빠른 프로토타이핑이 필요한 환경

	- 인터프리터의 경우, 코드작성 및 수정부터 실제 실행까지의 과정에서 별도의 명시적인 AOT 빌드 과정이 생략된다. 적은 수의 실행이면 큰 차이가 없으나, AI 연구 등과 같이 `코드를 빠르게 수정하고 반복되는 환경`에서는 차이가 난다.
	- 구체적으로는 

1. 자동화 스크립트

    - 일부 인터프리터를 사용하는 언어의 경우(Python 등), 기본 라이브러리에 파일 접근이 가능한 명령어를 제공하기 때문에 비교적 편리하게 자동화 관리 스크립트를 작성하는 데 유리하다.
    - 추가적으로, 관리 프로그램의 경우 반복해서 수정할 일이 많아질 수 있는데, 이런 점에서 인터프리터를 사용하는 언어가 컴파일러를 사용하는 언어보다 유리하다.
    - 다만 이는 인터프리터 자체의 기능이 아니라, 각 언어의 설계와 라이브러리의 생태계가 결합된 결과이다.

1. 대화형 데이터 분석

	- 명령 후 결과를 받고, 그 결과를 확인하면서 다음 명령을 내릴 수 있으므로 분석이 굉장히 편해진다.
	- 컴파일의 경우 결과 수령 후 다시 컴파일을 수행해야 하므로 시간소요가 비교적 많아진다.
	- 이 또한 인터프리터 자체의 장점은 아니며, REPL과 노트북 환경의 장점이다. 컴파일 방식의 언어도 REPL을 제공할 수 있다.

1. 게임 스크립트 변경

    - 데이터 변경이 아니라, 게임 로직(NPC의 행동 로직 등)을 변경할 때, 게임 전체가 컴파일러를 사용하게 되면 NPC하나의 행동을 변경해도 전부를 다시 빌드해야 한다. 인터프리터 언어를 사용할 땐 수정할 게임 로직의 파일만 바꿔줘도 손쉽게 수정이 가능하다.
        > 컴파일 언어도 중분 빌드, 동적 라이브러리, 모듈 교체, 핫 리로드 등의 방식으로 전체 재빌드를 피할 수 있다.\
		>Lua를 사용한다고 해도 엔진이 핫 리로드를 지원하지 않으면 즉시 변경이 불가능하다.

    - 언리얼에서도 C++과 엔진으로 만든 시스템 위에 Lua(인터프리터 언어 중 하나)를 얹어 세부적인 게임 로직을 구성하는 경우가 많다고 한다.
    	> 게임 서버 : C++, 언리얼 엔진으로 서버 내용 변경시 재빌드 필요\
		> NPC,퀘스트 등 세부 로직 변경 : Lua파일만 수정하여 배포

이외의 환경에서도 `개발 속도`, `생산성`, `유지보수`, `반복 수행`, `확장성` 등이 중요한 환경에서는 실행 성능이 강점인 컴파일러보다 인터프리터가 유리하게 사용될 수 있다.
