# 가비지 컬렉션(Garbage Collection,GC)

- 프로그램이 더 이상 사용하지 않는 메모리를 자동으로 찾아서 해제하는 기능

- C/C++에서는 보통 개발자가 직접 메모리를 관리해야 하지만, C#에서는 `new`키워드만 사용하고, 메모리 해제는 ==CLR==의 ==GC==가 자동으로 수행한다.

### GC의 기본 아이디어

- 객체를 `new`키워드를 사용하여 활용하다가, 해당 객체가 null이 되거나, 스코프를 벗어나 함수가 종료되면, 해당 객체를 참조하는 변수가 없는 상태가 된다.
- 이렇게 GC가 누구도 참조하지 않는 객체를 발견하면, 메모리를 회수한다.

### 알고리즘

- Mark and Sweep

	- GC의 대표 알고리즘

	1. Mark

    	- GC는 Root부터 탐색한다.
    	- 사용중인 객체는 Mark하고, 사용중이지 않는 객체는 Mark하지 않는다.

	1. Sweep

    	- Mark되지 않은 객체는 제거한다.

- Compact

	- 만약 Mark and Sweep등의 방법으로 메모리를 회수했는데, 메모리 내에 단편화가 발생하면 메모리를 압축(Compaction)한다.
	- 이런 역할을 하는 GC를 ==Compacting GC==라고 한다.

- .NET GC의 세대(Generation)별 관리

	- 각 객체마다 세대를 부여하여 관리한다.

    	> GameManager이나 Player같은 객체의 경우 게임 시작부터 종료까지 존재할 수 있지만, 그 외의 객체는 생성 직후에 사라질 수도 있다.

	- 쉽게 말해 짧게 사는 객체와 오래 사는 객체를 분리하여 관리한다.

	- Generation 0

    	> 가장 어린 객체\
		> GC가 가장 자주 검사한다.

	- Generation 1

    	> Gen0에서 살아남은 객체
		> Gen0에서 한번 컬렉팅을 한 후 남아 있는 객체들이 Gen1로 승격한다.

	- Generation 2

    	> 오래 살아남은 객체\
		> Gen1과 마찬가지로 생존하면 승격한다.\
		> 보통 싱글톤이나 Manager계열들이 Gen2에 있다.

	- `객체는 금방 죽는다`라는 개념이 주요 근거.

- Large Object Heap(LOH)

    - 큰 객체(약 85KB 이상)은 이 영역에 저장된다.
    - 이런 객체들은 생성 직후라도 Gen0에 머물지 않고 Gen2와 비슷하게 관리된다.


### Unity와 GC

- Unity 개발에 있어서, 가능하면 GC를 피하는게 좋다.

	> 비용이 크기 때문에 게임 프레임 드랍이 쉽게 발생할 수 있기 때문

- GC Allocation

	- Unity Profiler에서 자주 보는 수치
	- 이번 프레임에서 새로 생성된 힙 객체 수
	- 없는게 좋고, 지속적으로 증가하면 나쁘다.

- Unity에서 GC를 유발하는 행동

	- 문자열 연결

    	> 단순한 연산으로 보이나, 실제로는 새 문자열을 생성하는 행위

	- LINQ

    	> 할당 발생 가능

	- foreach

    	> 컬렉션 종류에 따라 할당 발생 가능

	- Delegate / Lambda

    	> 항상은 아니지만, 상황에 따라 할당 발생

	- Instantiate / Destroy

    	> 명백하게 GC대상이 늘어난다.\
		> 이를 해결하기 위해 `Object Pooling`을 사용한다.
