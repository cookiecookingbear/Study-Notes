# 컴파일러

- 언어나 중간 표현으로 작성된 프로그램을 그 **의미를 보존하면서 다른 언어나 프로그램 표현으로 변환**하는 언어 처리기

- 컴파일 결과가 반드시 기계어일 필요는 없다.

## [컴파일러 관련 예상 기술면접 질문](./Interview_questions/컴파일러_예상질문.md)

## 소스 언어, 타깃 언어

- 소스 언어 : 변환 전 프로그램 언어
- 타깃 언어 : 변환 후 프로그램 언어

## 동작 과정

1. 어휘 분석(Lexical Analysis)

	- 소스 코드의 문자열을 의미 있는 최소 단위인 토큰으로 나눈다.
	- 어휘 분석을 수행하는 구성 요소를 `렉서(Lexer)`, `스캐너(Scanner)`, `토크나이저(Tokenizer)`라고 한다.

1. 구문 분석(Syntax Analysis)

	- 토큰이 해당 언어의 문법에 맞게 배치되었는지 검사하고, 프로그램의 구조를 나타내는 구문 트리를 만든다.
	- 대표적인 결과가 AST(Abstract Syntax Tree, 추상 구문 트리)다.

1. 의미 분석(Semantic Analysis)

	- 구문 분석에서 문법을 검사한 후, 의미 규칙에도 부합하는지 검사한다.

1. 중간 표현(IR) 생성

	- 추상 구조 트리를 곧장 기계어로 변환하지 않고 중간 표현(Intermediate Representation)으로 변환하는 경우가 많다.

    	- IR을 거치는 이유

        	1. 소스 언어의 복잡한 문법을 단순한 연산으로 표현
        	1. 최적화
        	1. 여러 소스 언어에서 공통 백엔드 사용
        	1. 소스 언어와 타깃 CPU 사이의 결합 감소


## 컴파일러가 사용하는 주요 자료구조

1. 심벌 테이블(Symbol Table)

	- 컴파일러가 이름과 관련된 정보를 관리하기 위해 사용하는 자료구조
    
		- 변수/함수/클래스/구조체/매개변수 등의 이름
		- 타입
		- 유효 범위
		- 선언 위치
		- 저장 위치
		- 접근 제한자 등을 저장

	- 일반적으로 실행 중인 변수의 현재 상태를 저장하는 런타임 저장소는 아니다.
	- 심벌 테이블은 역할을 나타내는 개념이다
    	> 특정 자료구조를 뜻하지 않으며, 심벌 테이블을 구현하기 위해 해시 테이블, 트리, 배열, 스택 등과 이들의 조합을 사용할 수 있다.
	
	- 컴파일러는 심벌 테이블을 이용해서 `이름 해석`, `중복 선언 검사`, `스코프 처리`, `타입 검사`, `함수 호출 검사`, `코드 생성`, `오류 메세지 생성` 등의 작업을 수행한다.


## 구조

1. 프런트엔드

	- 프런트엔드는 소스 언어를 이해하고 중간 표현으로 변환한다.

    - 주로 `어휘 분석`, `구문 분석`, `AST 생성`, `이름 해석`, `타입 검사`, `초기 IR 생성` 등을 수행한다.
    - 프런트엔드는 주로 소스 언어에 종속적이다.

1. 미들엔드

	- 중간 표현을 분석하고 최적화한다.

    - 주로 `제어 흐름 분석`, `데이터 흐름 분석`, `불필요한 연산 제거`, `상수 계산`, `함수 인라이닝`, `루프 최적화`, `벡터화`, `공통 부분식 제거` 등을 수행한다.
    - 특정 소스 언어나 CPU에 대한 의존성을 줄인 상태에서 동작하도록 설계되는 편이다.

1. 백엔드 

	- IR을 특정 타깃 아키텍처와 실행 환경에 맞는 코드로 변환한다.

	- 주로 `명령어 선택`, `레지스터 할당`, `명령어 스케줄링`, `호출 규약 적용`, `메모리 주소 계산`, `타깃별 최적화`, `어셈블리/기계어 생성` 등을 수행한다.
	- 백엔드는 주로 타깃 CPU와 실행 환경에 종속적이다. 

### 프런트엔드와 백엔드를 분리하는 이유

- 언어(프런트엔드)와 CPU(백엔드)조합마다 컴파일러 전체를 새로 만들지 않기 위해

- 프런트엔드, 미들엔드, 백엔드의 세 구분으로 깔끔하게 분리되지 않을 수 있다.

## 코드 최적화

### 컴파일러 최적화

- 컴파일러 최적화 : 프로그램의 관찰 가능한 의미를 유지하면서 `실행 시간`, `코드 크기`, `메모리 사용량`, `전력 소비`, `캐시 활용`, `특정 CPU자원 활용` 중 하나 이상을 개선하는 변환
- 단, 최적화를 진행한다고 해서 반드시 성능이 좋아지는 것은 아니다.
		
	> 실행 속도를 높이면 코드 크기가 커질 수 있고, 컴파일 시간이 증가할 수도 있다.

### 대표적인 컴파일러 최적화

- 상수 폴딩

	- 컴파일 시점에 계산할 수 있는 값을 미리 계산한다.

- 죽은 코드 제거

	- 실행될 수 없는 코드를 제거한다.
	- 실행되더다로 결과가 사용되지 않고 프로그램의 관찰 가능한 동작에 영향을 주지 않는 코드도 제거한다.

- 공통 부분식 제거

	- 소스 코드 내 공통된 연산이 있다면 한번만 계산하여 재사용할 수 있다.

- 함수 인라이닝

	- 함수 호출 대신 함수 본문을 호출 위치에삽입할 수 있다.

	- 함수 호출 비용을 줄이고 추가 최적화 기회를 만들 수 있지만, 지나친 인라이닝은 코드 크기를 증가시킬 수 있다.

- 루프 최적화

	- 루프 불변 코드 이동
	- 루프 펼치기
	- 루프 결합과 분리
	- 벡터화

- 레지스터 할당

	- IR의 임시 값과 변수들을 느린 메모리 대신 제한된 물리적 CPU레지스터에 배치하도록 결정한다.
	- 값이 사용되는 범위, 동시에 유지되어야 하는 다른 값, 사용 빈도, 호출 규약 등을 고려할 수 있다.
	- 단, 레지스터의 잔여 용량이 부족하면 일부 값을 메모리로 옮기는 스필(Spill)이 발생할 수 있다.

## 컴파일 결과물

- 컴파일 결과가 반드시 실행이 가능한 파일이 되는 것은 아니다.

- 실행 파일 말고도 `어셈블리 코드`, `목적 파일`, `네이티브 실행 파일`, `바이트코드`, `중간 표현`, `다른 고수준 언어`, `.lib 혹은 .dll에 들어갈 코드`가 될 수 있다.

- 컴파일 결과물에 대해 자세히 알아보기 위해, C 계열의 일반적인 빌드 과정을 살펴보면,
	
	> 소스 파일 - 전처리 - 컴파일 - 어셈블 - 목적 파일 - 링크 - 실행 파일

	의 순으로 진행된다.

- 위의 과정으로 만들어진 실행 파일은 로딩을 거쳐 실제 프로그램을 실행한다.

### 전처리기(Preprocessor)

- C/C++에서는 본격적인 컴파일 전에 전처리기가 동작할 수 있다.

    > C#에서는 `#if`, `#define`, `#nullable`등의 전처리기 지시문이 존재는 하나, C/C++의 동일 명령어와는 다른 역할을 한다. C#에서는 어휘 분석 단계에서 위의 명령어를 처리한다.

- 주로 `헤더 파일 포함`, `매크로 치환`, `조건부 컴파일` 등의 작업을 진행한다.

### 어셈블러(Assembler)

- 어셈블리 코드를 기계어가 포함된 목적 파일로 변환한다.

- 어셈블러도 넓은 의미에서는 언어 번역기지만, 일반적으로 고수준 언어 컴파일러와 별도의 도구로 구분한다.

- 컴파일러가 곧장 목적 파일(목적 코드)를 생성하는 경우도 있다.

### 목적 파일(Objectd File)

- 목적 파일에는 `기계어 코드`, `데이터`, `심벌 정보`, `재배치 정보`, `디버깅 정보`, `다른 목적 파일이나 라이브러리에 대한 참조`, 등이 들어갈 수 있다.

- 보통 주소와 외부 참조가 완전히 해결되지 않아 단독으로 실행이 불가능한 경우가 많다.

### 링커(Linker)

- 여러 목적 파일과 라이브러리를 결합하고 심벌 참조를 해결하여 실행 파일이나 라이브러리를 생성한다.

- 링크 단계에서는 

	1. 함수가 선언되어 호출되었으나 내부 구현이 존재하지 않음
	1. 동일한 심벌이 중복 정의됨
	1. 필요한 라이브러리를 찾을 수 없음

	등의 문제가 발생할 수 있다. 이는 빌드 중 링크 단계에서 발생하는 오류로, 이 오류들이 컴파일 오류인 것은 아니다.

### 로더(Loader)

- 실행 파일을 메모리에 배치하고 프로그램이 실행될 수 있도록 준비한다

- 주로 `코드와 데이터를 메모리에 배치`, `필요한 동적 라이브러리 연결`, `주소 관련 처리`, `스택과 실행 환경 준비`, `프로그램 진입점으로 제어 이동` 등의 작업을 수행한다.

- 로더는 컴파일러가 아니라 운영체제 및 런타임의 실행 준비 구성 요소에 가깝다.

## 컴파일러의 종류

- 이하의 컴파일러 종류는 서로 배타적인 종류가 아니라 컴파일 시점, 입출력 형태, 실행 환경, 재컴파일 범위 등 서로 다른 기준에 따른 분류다.
- 따라서 하나의 컴파일러가 AOT컴파일러면서 클로스 컴파일러이고 증분 컴파일러일 수도 있다.

1. AOT 컴파일러

	- Ahead-Of-Time 컴파일러는 프로그램 실행 전에 타깃 코드를 만든다.

	- 장점

    	- 실행 중 컴파일 비용 감소
    	- 빠른 시작 시간
    	- 배포 전에 충분한 분석 가능
    	- 실행 환경에 컴파일러가 필요하지 않을 수 있음

	- 단점

    	- 타깃 플랫폼별 결과물이 필요할 수 있음
    	- 컴파일 시간이 필요함
    	- 실제 실행 중에만 알 수 있는 정보를 활용하기 어려울 수 있음

1. JIT 컴파일러

	- Just-In-Time 컴파일러는 프로그램 실행 중에 중간 코드 등을 네이티브 코드로 변환한다.

	- 실행 중에 작동하지만, 프로그램 표현을 다른 프로그램 표현으로 변환(실행하는 것이 아닌)하므로 인터프리터가 아니다.

	- 실행 중에 발생한 정보를 활용할 수 있다.

	- 단점

    	- 실행 중 컴파일 비용
    	- 워밍업 시간
    	- 런타임 메모리 사용
    	- 성능 변화의 예측 어려움
    	- 구현 복잡도

1. 트랜스파일러

	- 작성된 고수준 언어를 다른 고수준 언어로 변환한다.
	- 타깃 언어가 비교적 고수준인 컴파일러를 구분해 칭하는 실용적인 용어에 가깝다.

1. 크로스 컴파일러

	- 컴파일러가 실행되는 플랫폼과 결과 프로그램이 실행된 플랫폼이 다른 컴파일러

	- 호스트 : 컴파일러가 실행되는 환경
	- 타깃 : 생성된 프로그램이 실행되는 환경

1. 증분 컴파일러
   
	- 전체 프로그램을 매번 다시 컴파일하지 않고 변경된 부분과 영향을 받는 부분을 중심으로 다시 컴파일한다.

	- `규모가 큰 프로젝트`, `IDE의 실시간 오류 검사`, `빠른 반복 개발`, `대규모 빌드 시스템` 등에서 중요하게 사용된다.

1. 자체 호스팅 컴파일러

	- 자신이 컴파일하는 언어로 작성된 컴파일러를 자체 호스팅 컴파일러라고 한다.
	- 이러면 닭이 먼저냐, 알이 먼저냐의 문제가 있다. 초기에는 다른 언어로 작은 컴파일러를 만들고, 이를 이용해 새 컴파일러를 컴파일 하는 방법을 사용할 수 있다. 이 과정을 `부트스트래핑`이라고 한다.

## 컴파일 방식의 장점과 비용

- 아래의 특성들은 모든 컴파일러에 동이랗게 적용되는 장단점이 아니다.
- 컴파일 시점, 생성되는 타깃 코드, 최적화 수준, 언어의 타입 체계, 런타임 구성에 따라 달라질 수 있다.

### 장점

1. 실행 전 작업 수행

	- 실행 전에 작업을 수행하므로 실행 중의 부담이 적어진다.

1. 최적화

	- 프로그램 전체나 큰 범위를 분석하여 최적화할 수 있다.

1. 오류 조기 발견

	- 실행되기 전 오류를 발견할 수 있다.

1. 소스 없이 배포 가능

	- 기계어, 바이트코드, 라이브러리 등의 형태로 배포할 수 있다.
	- 하지만 컴파일 결과물 자체도 역공학이 가능하긴 하다.

1. 타깃에 특화된 코드 생성

	- CPU 명령어, 레지스터, 캐시 특성, 호출 규약 등을 고려한 코드를 생성할 수 있다.

### 한계 요소 / 비용

1. 빌드 시간

	- 프로젝트가 크고 최적화 수준이 높으면 컴파일 시간이 길어질 수 있다.

1. 플랫폼 의존성

	- 네이티브 코드는 특정 CPU, 운영체제 등에 종속될 수 있다.
	- 바이트코드를 생성하는 컴파일러는 플랫폼 의존성을 런타임 쪽으로 옮길 수 있다.

1. 디버깅 복잡성
